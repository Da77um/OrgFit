## Phase 06 decisions — 2026-09-09

| ID | Selected implementation and consequences | Evidence / boundary |
|---|---|---|
| D-048 ACCEPTED development implementation | DEPARTMENT targeting is flat: it resolves the named department's own active members once, at launch, and never rolls up descendant departments. Options considered were flat membership, recursive descendant rollup, and an operator-chosen switch. Flat was selected because the frozen privacy policy already declares `segmentation: FLAT_DEPARTMENT` and a recursive target would silently produce a report group whose membership does not match its label. Staff who want a subtree select its departments explicitly through SELECTED. | `core.resolve_target`; department-target and launch-freeze tests in `tests/campaigns.test.ts`. | D-049 ACCEPTED development implementation | Invitation credentials are 256-bit random tokens stored only as an HMAC-SHA256 keyed digest with a recorded `digest_key_version`; `INVITATION_DIGEST_KEY` is a separate secret from the import key. ## Phase 07 decisions — 2026-09-09

No earlier privacy decision is weakened here. D-017, D-018, D-026, D-027, D-029 and D-030 are implemented as written; where this phase had to choose between two readings, it chose the stricter one and recorded it below.

| ID | Selected implementation and consequences | Evidence / boundary |
|---|---|---|
| D-053 ACCEPTED development implementation | **Two new deployment identities, and both hold zero table privileges.** `orgfit_gateway` (the respondent origin) and `orgfit_processor` (the privacy processor) can execute only session-scoped or batch-scoped `SECURITY DEFINER` routines. Granting the gateway ordinary SELECT/INSERT on `intake` was rejected because a single query mistake would then expose every draft. `orgfit_staff` is granted **nothing** in schema `intake` — not even USAGE — so the two staff-callable routines (`core.register_campaign_key`, `core.release_readiness`) live in `core` and write into `intake` as their definer. | `db/migrations/009_intake.sql`; `gatewayReadiness()` asserts at runtime that the gateway holds no table privilege and is a member of no other role. Tests assert that `orgfit_staff` cannot name an intake object and that `orgfit_processor` cannot read a participant, an invitation, a draft, or call `intake.accept`. Consequence: every new respondent capability needs a new routine and an explicit grant, which is the intended friction. |
| D-054 ACCEPTED development implementation | **The key custody boundary is one-way even in development.** D-027 left custody open; a shared symmetric wrapping key would have let the staff process decrypt every campaign key it had ever created. Instead the custodian is an X25519 key pair: the staff process holds only `CAMPAIGN_KEY_CUSTODY_PUBLIC_KEY` and seals each campaign private key to it with `crypto_box_seal`, and only the processor holds the secret half. A campaign key is created **inside the launch transaction**, so a campaign can never open for answers with nothing to seal an acceptance to; if custody is unavailable the whole launch rolls back. | `src/key-custody.ts`, `src/campaigns.ts` launch, `core.register_campaign_key`. Tested: launch without custody fails closed and leaves no campaign OPEN without a key; one campaign's key cannot open another's envelope. Boundary: this is a local stand-in for a managed key service, not an HSM, and it provides **no backup-safe crypto-erasure** — a backup taken before destruction still holds the sealed key. Real custody remains P-003. |
| D-055 ACCEPTED development implementation | **A live session on an accepted invitation is kept, not deleted.** The first implementation deleted sibling sessions inside `intake.accept`. That made the required "retry after a lost success response returns generic acceptance" behave as `SESSION_REQUIRED` for a second tab, which is both wrong and confusing. Sessions now survive acceptance; every draft routine refuses them with `ALREADY_ACCEPTED` and `accept` returns the same generic `ACCEPTED`. Rotation and revocation still delete sessions, because there the credential itself has changed. | 100-way concurrency test: exactly one `ACCEPTED`, 99 generic duplicates, one inbox row, first payload byte-identical afterwards. |
| D-056 ACCEPTED development implementation | **The respondent origin is the gateway and therefore legitimately links a PostgreSQL driver.** The Phase 02 boundary check forbade `pg` in the respondent build; that rule cannot survive a gateway that must reach the database. The rule is restated as the property it was protecting: the respondent build must contain no staff credential, no staff authentication, no staff query builder, no staff data module and no key-custody adapter, and the staff build must contain neither the gateway pool nor the processor. Both directions are checked, and `src/gateway-db.ts` / `src/config.ts` refuse to start a process holding a foreign credential. | `scripts/check:boundaries`, plus unit assertions on `assertNoForeignCredentials` and `gatewayUrl`. This is a restatement of D-014's intent, not a relaxation: the credential separation it protects is now enforced at runtime as well as in the build trace. |
| D-057 ACCEPTED development implementation | **Anonymous answers are keyed by the instrument's stable key, and the anonymous store is append-only to the processor.** Using the internal question id would let anyone holding two instrument versions line them up by identifier. The processor holds `SELECT` and `INSERT` on the anonymous schema and deliberately **no** `UPDATE` or `DELETE`, so committed content is immutable to the only credential that can reach it; whole-campaign retention purge is a separate custodial routine owned by `orgfit_anon_owner`. A trigger refuses to assign the COMPANY group to any individual response. | Migration `db/anonymous/001_anonymous.sql`; tests assert stable keying, immutability denial, and the COMPANY refusal. |

### Defects repaired in this phase and at Checkpoint C

| ID | Defect | Repair |
|---|---|---|
| R-001 | Migration 005 wrote the questionnaire-version rule as `(state='DRAFT' AND …) OR (state<>'DRAFT' AND octet_length(schema_hash)=32 AND …)`. With `schema_hash` NULL the second branch evaluates to NULL, the whole CHECK is NULL, and PostgreSQL **accepts** the row — so a PUBLISHED version could carry no content hash. Phase 07 binds every accepted envelope and every anonymous manifest to that hash, so a null one would silently disable a real integrity check. | Migration 009 restates the constraint with an explicit `schema_hash IS NOT NULL`. The `ALTER` validates existing rows. Found by the Phase 07 fixture, which published a version without passing its document. |
| CC-001 | Found by **Checkpoint C**. The sub-five purge path in `src/processor.ts` unlinked the sealed campaign key file but never called `intake.keys_destroyed`, so `intake.campaign_key.state` stayed at `DELETE_REQUESTED` for ever with no destruction evidence recorded — for exactly the campaigns the blueprint wants erased soonest. An operator auditing key state could not distinguish it from a genuinely stalled destruction. | Destruction is now recorded on the suppressed path, ordered after the terminal `PURGED` transition so the batch state is preserved (`keys_destroyed` only advances a batch still in `CLEANUP_PENDING`). Regression test in `tests/privacy.test.ts` asserts `DESTROYED`, the evidence text and the preserved `PURGED` state. |

No business behaviour, permission, privacy control or lifecycle changed; the decisions below are about how the product is drawn, and about two latent defects the work exposed.

The identity's own vocabulary is used throughout — **ink** (`#191614`), **limestone** (`#E4DCCF`/`#EFE8DD`/`#F7F3EC`), **clay** (`#9A4E2A`), the **rhombic unit**, and the rule stated in its greyscale proof: *the information is in the shape, not the colour*.

| ID | Selected implementation and consequences | Evidence / boundary |

| D-091 ACCEPTED development implementation | **Three token layers, and a component may only read the middle one.** `src/theme.css` declares layer 1 BRAND (`--brand-ink`, `--brand-limestone-*`, `--brand-clay*`) in the identity's own words, layer 2 SEMANTIC (`--surface`, `--text`, `--border`, `--action`, `--accent`, `--danger`…) which is the only layer a rule below is allowed to reference, and layer 3 COMPONENT (`--chart-scale-*`, `--appbar-height`, `--rail-width`).
