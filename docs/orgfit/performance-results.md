# Performance results (Phase 14)

2026-09-14. Measured, not assumed. Harness: `tests/ops/load.ts`; raw output: `work/p14-load.json` (ignored, regenerated by running the harness).

## What was measured and what was not

**Measured:** real route handlers and gateway functions, real PostgreSQL routines, real runtime credentials and the production pool size (10 connections per role), in one Node process, against one local PostgreSQL. The directory rows were bulk-inserted by an operator statement; everything else — instrument publication, campaign launch, link issuance, sessions, encrypted drafts, submissions, processing, release, results reads and report rendering — used product code.

**Not measured:** HTTP, TLS, a reverse proxy, network latency, browsers, multiple application instances, a managed or separate database host, replication, or production data volumes over time. Figures are **application + database latency on one developer machine**, not end-user latency and not a capacity guarantee. The load generator shares the CPU with the service, which makes concurrency figures pessimistic for the service and optimistic for the network.

## Defects the measurements found, and their repairs

### PERF-1 — row security evaluated per row (repaired, migration 018)

The first run **could not list participants at all**: the staff statement was cancelled by the statement timeout. Seven staff read policies called `access.has_org(organization_id)` and `access.has_capability(...)` as plain expressions, which PostgreSQL evaluates for every row; each call resolved the session again, and security-definer functions are never inlined. At 100,000 rows that is 100,000 session lookups per page.

Repair: `018_policy_performance.sql` rewrites the seven policies so every session-dependent term is a scalar sub-select — evaluated once per statement as an init plan — and organization membership becomes `organization_id = ANY(<caller's organizations>)`, which an index serves. **The rules did not change.** `tests/operations.test.ts` O-8 applies 017, records exactly which rows an administrator, an assigned member, an unassigned member and a caller with no session can see in all seven tables, applies 018, and asserts the result is identical (and that the three callers genuinely see different rows).

### PERF-2 — the pinned instrument rebuilt on every respondent request (repaired)

The first concurrent run: **75 of 200 sessions failed**, instrument load p50 1.35 s, final acceptance p95 3.18 s (over target). Every exchange-to-finalize request asked the database to aggregate the full node tree of the 200-item version and re-inflate it — twice for a submission. (Error codes were not captured in that run; the harness was extended to record them before the repair was measured, and the repaired run recorded none.)

Repair: a published version is immutable and hash-identified, so the gateway now keeps the inflated tree in a bounded in-process map keyed by **version id and schema hash**, and every request still resolves the session in the database through a new lightweight routine, `intake.gateway_instrument_ref`, which performs the same checks as `gateway_instrument` without shipping the tree. Each caller receives its own copy. What is cached is the questionnaire, identical for every respondent — never a session, draft or answer. The existing respondent, privacy and Checkpoint C suites pass unchanged.

## Remaining performance risks

1. **Final acceptance at 200 simultaneous submissions is 2.1 s p95** on this machine with one 10-connection pool. Acceptance deliberately serializes on the campaign and invitation locks; more instances do not remove that. Real simultaneity is far lower than "200 in the same second", but the margin should be re-measured on production hardware (P-002).
2. **No HTTP-level load test** was run: production builds refuse to start without TLS and verified database TLS, which this machine does not have. The staging rehearsal in Phase 15 must measure through the real proxy.
3. **Name search scans the organization's participants** (88 ms at 100,000). Acceptable at the baseline; a trigram index would be needed well beyond it.
4. **Processing time grows with responses × items** (9.9 s for 40,000 answers). A 10,000-respondent campaign on 200 items is roughly 2 million answers and was not processed here; extrapolating linearly is not evidence. It runs as a background job with a lease, so it does not block respondents, but its duration and memory should be measured before a campaign of that size.
5. Retention and anonymous purges run in batches (5,000 rows, 50 campaigns) and were only exercised at test scale.
