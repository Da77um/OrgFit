# OrgFit privacy protocol and release contract

2026-09-08 · Phase 01 design baseline · NOT independently verified

This document specifies how standard primitives and transactions are to be used; it is not a new cryptographic construction or proof of anonymity. Production still requires P-001–P-008 in [decisions.md](decisions.md). No keys, encryption code, database behavior or production data were created in this phase.

## 1. Trust boundary and observable data

Identity/completion remains in core. Browser-key-encrypted drafts and processor-key-encrypted intake are restricted temporary storage in the same PostgreSQL database as invitations, enabling atomic acceptance. Finalized responses/scores live in a different database, with no participant, invitation, token, draft, session, envelope, IP/UA, precise timestamp, answer checksum or actor fields. Staff and report-worker credentials cannot connect there. Safe immutable snapshots are the only analytics read path. No per-person completion update timestamp or audit event is exposed to staff.

Transient identity context and plaintext coexist in the respondent browser, privacy-path TLS terminator, gateway final/review validation memory, and processor input/decryption memory. Administrators combining ciphertext backups with keys could reconstruct the association. Browser extensions, modified survey JavaScript, processor/infrastructure collusion, traffic correlation and self-identifying text are outside the baseline guarantee. No request ID survives into processing. Named completion tracking itself discloses participation. Five contributors and mixing reduce specified disclosure risks but are not mathematical anonymity or differential privacy.

The public origin, TLS proxy/body inspection, error tracker and gateway belong to the trusted privacy deployment boundary. No third-party survey scripts, request/response body capture, bind parameters, crash form breadcrumbs, debug heap dumps or session replay. Private input metadata never goes into a generic queue or dead-letter body. Operational logs contain sanitized aggregate error counters and campaign/batch totals only. Administrative audit is separate and may identify staff, not submitted answer events. Network/backup access and retention require actual deployment review.

## 2. Invitation and session protocol

Generate 32 random token bytes using the runtime cryptographic RNG. Encode unpadded base64url; fragment link `/s#token=...` is displayed only at issuance/rotation or in an explicit encrypted short-lived manual export. Exchange via POST, remove fragment immediately, no-referrer/no-store; no token in query/path/logs. Store HMAC-SHA-256 digest under a dedicated versioned managed secret; constant-time comparison where comparisons occur in application. The digest is not an anonymous answer identifier and never leaves identity intake.

Launch freezes unique invitations without authenticating secrets (generation 0). Issuance sets generation 1/digest atomically; rotate unused invitation increments it under lock and invalidates old sessions. Do not retry by reissuing the same plaintext from a durable cache. Lost issuer reply is recovered by explicit unused-link rotation. No administrator draft impersonation endpoint exists. A copied bearer can still submit or discard progress; OrgFit cannot prove the human identity without changing the accountless model.

Session credential: 32 random opaque bytes, hashed server-side, host-only HttpOnly/Secure SameSite=Lax cookie on public origin. Development TTL: 30 minutes, refresh only while valid up to 12-hour absolute expiry. Every operation validates current invitation generation; no long-lived cached revocation decision. New device uses original current link for session and the private resume code for decryption. Staff sessions use separate origin/cookie/digest store, development idle30min/absolute12h and current staff auth_epoch/MFA; OIDC recovery/provider values remain production inputs.

### 2.1 Manual link export recovery

Bulk link export is the explicit exception allowing short-lived recoverable links. The issuer authorizes actor/org and locks campaign then selected READY invitations in sorted ID order, validates expected generations and any confirmed rotation, generates tokens, seals the complete export file to a dedicated temporary export key, and commits all new digests/generations plus encrypted_payload/key reference in `ops.private_export` together. If it crashes before commit, neither tokens nor export exist; after commit a worker retries copying the same ciphertext to private storage. It never regenerates different links on retry. An authorized issuer download decrypts the existing file in memory after current campaigns.manage/org checks. Generic staff/report/export worker credentials cannot select/decrypt the blob. Temporary export key is distinct from processor and draft keys; both stored ciphertext and usable key copies expire within 24h under approved custody policy. If encryption/key service is unavailable before commit, fail without rotating any invitations. This preserves transactional generation while avoiding a plaintext idempotency cache.

## 3. DF1 encrypted draft format

Selected development primitive: Web Crypto AES-GCM with 256-bit random browser-generated key, 96-bit fresh random nonce for every encryption, 128-bit authentication tag. This uses standardized authenticated encryption from [Web Crypto](https://www.w3.org/TR/webcrypto/), not a password-derived or invitation-derived cipher. Key is never sent to server. Use a reviewed maintained wrapper around the standard API and known-answer/tamper tests before implementation acceptance. No algorithm fallback on decryption failure.

DF1 private resume code is a locally parsed versioned encoding of `{version:"DF1",handle:randomUUIDv4,key:base64url32bytes}`. Encoding is not encryption; code is a secret. The server handle is independent of the key and invitation token. A code alone is not server authentication. Same-device storage contains local encrypted data and resume material under the dedicated survey origin; tell respondents shared-device users/extensions can access browser storage. Do not claim browser local storage is equivalent to hardware-protected key storage. Clear on confirmed acceptance/start-over; offer explicit local removal.

Ciphertext plaintext is UTF-8 JSON `{schemaVersion:1,versionId,answers:AnswerSet.answers,locale}` with no identity/timing metadata. Partial mandatory answers are allowed in drafts. Additional authenticated data is UTF-8 JSON array `["OrgFit","DF1",handle,versionId,nextRevision]`, using canonical UUID/text and integer representation. Browser creates handle before initial POST, so AAD is known; first revision=1, subsequent revision=expected+1. Header `{cipherVersion,handle,nonce,revision}` is bound by AAD except nonce already authenticated by GCM. Server authenticates request/binding and stores opaque bytes; it cannot validate decryption/tag itself without key. Client checks returned handle/version/revision before decrypting. Malformed ciphertext fails locally without sending key or plaintext in error reporting.

Never reuse nonce under the same key, including retry/conflict/offline paths. Random nonces avoid multi-device counter races; each re-encryption uses a new random nonce. Retrying the exact same encrypted bytes is safe only as a transport retry, never for a different plaintext. Conservative per-key limit is 2^20 encryptions; rotate local key and handle through confirmed draft replacement before the limit. This is a design cap, not evidence of a verified implementation. Expected-revision checks prevent silent overwrite/replay by normal clients; a malicious server or browser is outside this protection.

Create/save/resume/start-over/finalization all recheck valid current invitation session, campaign open and READY. Draft DB row has one invitation binding and only ciphertext, handle, revision, expiry. No staff SELECT or lookup. Cross-device: exchange original link, enter private code locally, send handle only to fetch ciphertext, decrypt locally, resolve any revision conflict before saving. Lost key means explicit confirmed discard/start-over; staff cannot recover. Thirty-day write-renewed idle expiry, bounded by closure+7d; no renewal via viewing/status. After closure, retained draft is inaccessible pending purge. API responds with truthful expiry/save status.

## 4. IN1 encrypted acceptance and key custody

Selected development primitive: libsodium sealed box to a per-campaign public key using the library's documented API. [Sealed boxes](https://doc.libsodium.org/public-key_cryptography/sealed_boxes) provide recipient-only decryption and ciphertext integrity, not sender authentication. Sender authorization is the validated session plus narrow gateway database routine. Do not invent signatures, a custom hybrid cipher or an identity-hashing anonymity mechanism.

Campaign launch requires an authenticated public key record from the isolated custody service before issuing links/acceptance. Each campaign has its own key pair; rotation creates a new epoch for that campaign, retains previous decrypt-only epochs until the entire campaign is transferred/purged. Private keys are never in core/anonymous databases, application environment files, staff process or generic backups. Gateway caches public keys through authenticated service identity, pins key reference/epoch to campaign and fails closed on untrusted/missing keys. Processor retrieves private use through its separately authorized custody service. Real provider/region and KMS wrapping/deletion APIs are P-002/P-003, not assumed to support a chosen native key algorithm.

Validated plaintext envelope before sealing: `{protocol:"IN1",envelopeId,organizationId,campaignId,invitationId,versionId,instrumentHash,reportGroupId,answers}`. Gateway selects every context field from locked frozen state. After decryption the processor compares context to outer envelope/batch manifest, preventing accidental ciphertext substitution between invitations/campaigns. This metadata is intentionally identity-linked staging, then stripped; none of envelopeId/invitationId or their hashes reaches the final store. There is no saved validation timestamp. Encrypted payload max2MiB. Unexpected key/version/manifest/context/answer validation failure blocks whole batch; do not quietly discard a person's accepted input.

Acceptance transaction is exactly [state-machines.md](state-machines.md) §4: campaign then invitation lock, authoritative wall-clock sample after validation/encryption, unique inbox insert+COMPLETED+draft deletion together, durable commit before ACCEPTED. Public review is transient validation only. Key service failure causes retryable failure before consuming invitation. No external queue/decrypt operation is required for acceptance success. Pending work is found from durable campaign/inbox state even if enqueue fails.

## 5. Full-batch transfer and crash recovery

At CLOSED, the processor locks campaign and creates one processing_batch with a fresh random stable batch ID, accepted count and sanitized frozen-manifest hash. Count of COMPLETED must equal inbox rows before first cleanup. Assign all input envelopes to this batch in the same core transaction. Row IDs/order/checksums are never used to derive output IDs. Lease generation fences cleanup/status operations; the anonymous database UNIQUE campaign marker is the final duplication guard even if a stale worker is still running.

Below five accepted: no decryption for results, no anonymous rows; only INSUFFICIENT_DATA/suppression state, purge by short terminal retention. Cancellation is terminal purge-only even if count>=5: completion stays true, no analytics publication. For eligible CLOSED campaigns, load complete assigned ciphertext set, decrypt inside isolated process memory, validate envelope bindings, drop identity/transport metadata, retain only allowed coarse department or OTHER group, randomly shuffle using a cryptographic RNG and assign fresh UUIDv4 output IDs. COMPANY is computed over the set, never assigned as an individual's department. Every accepted response must survive validation or the batch fails.

Within one anonymous transaction insert sanitized campaign manifest/groups, responses/typed answers/versioned scores and processed_batch marker with count/hash/engine. Commit all or none. No staff-visible staging, no per-input output map. Initial capacity uses one whole-campaign transaction up to baseline 10k respondents/200 items; load/fault evidence must establish memory/transaction limits. If that cannot fit, an explicitly reviewed inaccessible staging design with one atomic visibility marker is required before scaling, never streaming partial results.

| Crash / uncertainty | Durable evidence and exact recovery |
|---|---|
| Before core acceptance commit | Both inbox/completion roll back; retry while eligible. No success response. |
| After acceptance commit / dropped success | COMPLETED is authoritative; status or retry returns ACCEPTED, never compares/replaces payload. |
| Before/after freeze transaction | No batch means recreate under campaign lock; existing batch means reuse same ID/count/hash/assigned set. Never freeze a different subset. |
| Decryption/scoring before anonymous commit | No marker => rolled-back/no visible output; retry entire frozen set. Dispose uncommitted memory/staging. |
| Anonymous commit response lost | Query marker using same campaign/batch; if unknown/unreachable wait/retry, never assume failure and append. |
| Marker exists but core still PROCESSING | Validate count/hash/engine against frozen batch, advance OUTPUT_COMMITTED; skip decrypt/insert and begin cleanup. |
| Two workers race / expired lease | Only matching lease generation mutates core state; one anonymous campaign marker commits, loser rolls back complete transaction then checks winner. A mismatched marker blocks as incident. |
| Output committed, cleanup partially done | Marker+batch/count proof authorizes remaining ciphertext/draft deletion and key destruction; missing input now is expected only for documented cleanup state. Never require original inbox count after successful cleanup. |
| Key destruction pending/fails | CLEANUP_PENDING, retry provider deletion/recovery-window verification; no release while usable source decryption material remains recoverable under this design. Alert; do not label requested deletion as erasure. |
| Key missing before verified output | Block, incident/recovery procedure; no re-open/re-submit or silent count adjustment. |
| Count/hash mismatch, corrupt envelope, partial restored stores | Block publication; isolate and reconcile known durable states. Do not mark person incomplete or omit accepted responses. |
| Safe snapshot write/commit response lost | Lookup org/campaign/release revision and content hash; same existing snapshot succeeds, conflicting hash blocks. No alternate partial release. |
| Report upload/registration lost | Only registered READY checksum-matched artifacts downloadable; retry generation idempotently, purge orphan bytes. |

## 6. Backup-safe cleanup and erasure

After output confirmation delete inbox and draft remnants, dispose plaintext memory and temporary files (no such files by default), request destruction of all campaign private-key epochs and record custody evidence. Destruction includes recoverable secret versions, provider recovery windows, wrapped copies and usable wrapping keys; deleting one current secret reference is insufficient. If infrastructure cannot meet this, publication stays CLEANUP_PENDING until review resolves it, rather than silently weakening the baseline. Provider deletion latency therefore affects result availability and must be selected consciously before real use.

Keep only batch/campaign count, manifest/hash/status and coarse cleanup evidence; remove envelope assignments by deleting envelopes, never preserve input/output receipts. Separate encrypted backup schedules for core, anonymous and custody; core backup readers cannot decrypt intake. WAL/replicas/backups can retain ciphertext after row deletion; it is safe to claim crypto-erasure only after required keys are truly inaccessible. Key policy is campaign-granular, so deleting a processed campaign key does not break other campaigns. Draft server backups never contain browser keys; shared-browser risk remains independent.

Before any restored service is accessible, replay external deletion ledger/tombstones and all expired retention, disable old sessions, reconcile core accepted state versus batch/output markers, and verify key policy. A stale backup must never reopen consumed links. Restoring an earlier core with later anonymous data requires quarantined campaign reconciliation, not accepting new submissions. If both backups predate an acknowledged acceptance and no durable recovery evidence exists, that loss cannot be wished away: keep affected collection inaccessible and handle a data incident. A tested RPO target measures possible recovery loss; it does not prove zero-loss finalization.

Published snapshots and consulting records follow approved business retention. Anonymous answers expire by whole campaign after 12 months (proposed); directory erasure cannot target an anonymous individual's answers. Tombstones persist longer than all containing backups/key recovery windows. P-004 must approve durations; Phase 14 must test actual provider deletion/restore behavior. No real key destruction or data deletion happened in Phase 01.

## 7. Deterministic safe release algorithm

Release unit is one organization/campaign with one frozen policy/version and one reviewed snapshot. Result candidates containing protected numeric values remain only in processor memory/anonymous boundary; no staff-readable CANDIDATE stores hidden values. Safe snapshot creation and all safe cells commit atomically; publication status flips only when the complete package is validated. Recommendations use only safe approved values, never secret evidence. No live result values while collection is open.

Development release policy R1, deliberately conservative:

1. Validate accepted/processed counts and frozen instrument/engine/policy/group manifest; require confirmed output and cleanup. Calculate respondent metrics with explicit coverage/direction and decimal precision. Contributor set is distinct valid responses per metric, not invited/completed count. Unscored or invalid-coverage metrics cannot become zero.
2. Mark every metric with fewer than threshold valid contributors SUPPRESSED; distinguish whole-campaign insufficient, unscored and compatibility reasons without returning protected contributor counts. Mark sensitive homogeneous output withheld (numeric variance zero for sensitive score/item, including endpoints; categorical single occupied category; universal checkbox option presence/absence). No prose, exact dates, min/max raw answers, exact-value histogram labels or verbatim quotes in v1.
3. For each metric, consider one flat disjoint department partition including OTHER. If any nonempty group has <threshold valid contributors, remove **all** department cells/gaps/counts for that metric, leaving company candidate only if eligible. A department with zero valid contributions but roster/accepted members is conservatively treated as unsafe missingness and likewise removes the breakdown. No hierarchy/alternate partition or participant exclusions. Group roster size is never used as metric contributor count.
4. Distributions: use only predetermined semantically meaningful bins frozen with the definition. Require every released occupied bin and every nonempty complementary remainder to reach threshold. Suppress the entire distribution if this fails; do not publish a total that restores a hidden bin. Checkbox option membership and its complement each require threshold; if any option fails or overlaps make joint inference uncertain, withhold the whole checkbox distribution. No request-time merging chosen by staff.
5. Apply a fixed-point cross-metric check to all proposed outputs, including counts/coverage, bins, question scores, overall/dimension identities, direction transforms and gaps. Build measurement-dependency families from the pinned scoring definition (overall→dimensions→scored questions/matrix rows; derived distributions→item). If a protected metric could be constrained through other candidate members, conservatively withhold the related family outputs for that group instead of exposing a recoverable total. Unknown algebra/eligibility relationships are treated as unsafe. Department/company complement is handled by step 3, not by assuming independent cells. Re-run after suppression until no additional removal; uncertainty withholds the affected breakdown/family. This may withhold more than five-person thresholding alone.
6. Review proposed release jointly with all earlier released revisions and same-organization comparisons, including previously downloaded output that cannot be recalled. For ordinary first releases the fixed definition/partition prevents alternate query releases. For corrections, do not unhide formerly hidden metrics by default; preserve masks or further suppress, record correction/review rationale. Near-identical cross-round populations/background knowledge require review; no automated immunity claim. If supported comparisons/revisions allow reconstruction, withhold affected deltas/families or entire candidate until reviewed.
7. Serialize only safe values into SafeCell. Non-AVAILABLE: value, count, distribution and coverage all null, no hidden exact values or tooltip metadata. AVAILABLE numeric value is the approved full-precision decimal; display rounding is presentation-only, not a privacy control. Rule evaluation uses that same approved precision. Any rule referencing an unavailable input returns UNKNOWN/no match even if another branch could be true. Deterministic priority then stable key, exclusivity and dedup apply. Any derived label/ranking/gap that would imply a protected value is withheld.
8. Validate the final serialized package through the same contract used by UI/PDF/XLSX; persist content hash, versions, review reference and one immutable snapshot. Staff can track separate consultant actions but cannot modify computed evidence. Report worker gets only this package and safe organizational report metadata.

R1 is an implementable fail-closed release contract, not a theorem covering arbitrary external information. The implementation must demonstrate closure over its actual supported metric graph, metadata and outputs at Checkpoint D; an unimplemented checker cannot be replaced with UI hiding. If ambiguity remains at runtime, return status only for the implicated release, not a guessed safe number. No recommendation or export may act as an alternate disclosure channel.

Required adversarial design fixtures: 1/4/5 contributors; five total but four valid for one dimension; company12/department10+2 (company may remain, both department results removed); sparse categorical remainder; overlapping checkboxes; unknown/zero-valid groups; all-sensitive-equal answers; overall and other dimensions reconstructing a suppressed dimension; old versus corrected mask; and near-identical-round difference. Phase 01 reviewed their expected handling only, not an executable algorithm.

## 8. Design acceptance and future gates

The schema and APIs contain no retained direct identity bridge; atomicity, replay, closure/time, secret resume, complete batch marker, cleanup and one-time release are specified. Unresolved product contradictions: none requiring a baseline change. Conservative implementation choices and their availability/performance costs are recorded in decisions. The private processor remains explicitly trusted. Before production, independently review the actual cryptographic library bindings, key custody/deletion, browser delivery, logging, grants/WAL/backups, concurrency/recovery and complete disclosure algorithm. Written design alone does not verify them.

Phase 02 can proceed on the selected development foundation when requested. It must not implement later business modules or treat the production gates as approved. Stop after Phase 01.
